Why small models are fast — and why sparse ones aren’t local

Three different byte counts govern inference speed. They move independently, and almost every explanation collapses them into one.

The question

Two models get called fast, and they have almost nothing in common.

Kimi K3 is 2.8 trillion parameters. For any given token it activates about 104 billion of them — 16 of its 896 experts fire, plus the shared and dense components that run every time. So the work per token is a slice of the model rather than the whole thing. It is cheap to serve. You cannot put it on your laptop: the shipped checkpoint is about 1.56 TB even with 4-bit weights, and the published floor for running it is a single eight-card Blackwell-class node, or roughly four nodes if you are on 80GB H100s.

LFM2.5‑2.6B is 2.6 billion parameters and runs every one of them for every token. Quantized to 4 bits it is about 1.6 GB, decodes on a CPU or an NPU, and never touches the network.

Both designs make inference cheaper. They shrink different quantities, and the difference decides whether a model can live on your machine.

Two kinds of big number

One distinction first, because everything below is a byte count and the counts are easy to mix up.

Parameters describe the machine. A parameter is one number the model learned during training. It is fixed afterwards and identical for everyone who runs that model. Weight means the same thing about 99% of the time — strictly it refers to the parameters that multiply an input, as opposed to biases, which get added instead, but most current transformers drop biases entirely and nobody honours the distinction in conversation.

Tokens describe the material. A token is a chunk of text, roughly three quarters of a word, mapped to an integer. It is not part of the model. It changes on every request.

Both get quoted in billions and trillions, and that is the only property they share. Every number in the rest of this page counts one category, the other, or the two multiplied together — which is also why the list of numbers has three entries and not four.

Some geometry first, briefly

Once text is inside the model it stops being words. It is a matrix X, one row per token position, each row holding thousands of coordinates. More context means more rows. A wider model means more columns. Retrieval doesn’t expand what the model knows; it adds selected rows to the matrix currently on the desk.

A layer takes those rows and does two things. It measures — every output coordinate is a dot product against one learned direction, which you can also read as the matrix bending the whole coordinate space. Then it writes a correction back:

xℓ₊₁  =  xℓ  +  Δattention  +  ΔMLP

Writes are additive. The vector travels a residual stream collecting nudges — this word refers to that earlier noun, this is probably a physical object, a verb is coming. (Additive is not the same as permanent: later layers can and do write directions that cancel earlier ones.) Attention is how those nudges get sourced from other positions: queries ask, keys advertise, and the softmax over QK⊤/√dₖ decides how much of each value vector gets blended in.

At the end, one vector is compared against every vocabulary direction, a token is sampled, and it becomes a new row. Then the whole thing runs again.

Where the time actually goes

The usual line is that long context is slow because attention is quadratic. That’s true eventually and misleading at the lengths most people use.

Per layer, the attention scores and the value blend cost about 2n²d. The MLP and the Q/K/V/O projections together cost about 12nd². Set them equal and the crossover lands near n = 6d — for a model width of 4,096 that’s somewhere around 25,000 tokens, not 4,000. Below the crossover the linear-in-n work dominates: at a 2,000-token prompt it’s about twelve times the quadratic term, so doubling that prompt costs roughly 2.2×, not 4×. Above it the quadratic takes over, and at a million tokens it dominates by better than 40:1. That last regime is the one architectures are actually fighting.

Decoding is a different problem. Reading the whole prompt processes every token in parallel, so there’s plenty of arithmetic per byte of weights loaded — it’s compute-bound. Generating one token at a time is not: the hardware streams weights through to produce a single row, then does it again. At batch 1 that’s memory-bound, and it’s what you feel as tokens per second. Once the context is long enough, reading the cache back costs more than reading the weights, which is the link between the third number below and your token rate.

The three numbers

So there are three separate byte counts, and they move independently. Each one is the machine, the material, or the product of the two.

① Bytes of weights touched per token. Counts both. Parameters, multiplied by bytes per parameter, per token. This sets decode speed at batch 1, roughly bandwidth ÷ bytes-touched. Shrink it with sparsity, quantization, or a smaller model. It’s a roofline sketch rather than a law — at high batch, decode stops being memory-bound and this matters less.

② Bytes of weights that must be resident. Counts the machine only. Total parameters times bytes per weight, with no reference to what you are asking it to do. This one decides whether the model runs on your hardware at all. Quantization shrinks it. Fewer total parameters shrink it. Sparsity does not — an expert that fires for one token in fifty still has to sit somewhere the accelerator can reach. Streaming experts from CPU memory or NVMe exists, but every implementation trades the bandwidth back and is treated as experimental, not as a way out of this number.

③ Bytes of state that grow with the sequence. Counts the material only. The KV cache, proportional to n × (layers that keep one) × dₖₕ, doubled for K and V and multiplied by batch and bytes per element. The parenthetical is the part that matters here: in a hybrid model most layers may keep no growing cache at all.

“Active parameters” is ①. “Total parameters” is ②. A sparse model is one where those two numbers stop matching — that gap is the Mixture-of-Experts trick, and it’s why such a model can be cheap to serve and still impossible to run locally. So when one source says Kimi K3 is 2.8 trillion parameters and another says 104 billion, neither is wrong. They are quoting different entries from the list above.

Both companies spent their architecture budget on ③, and both did it the same way: make most layers carry a fixed-size state and leave real attention to a minority. Moonshot runs three linear-attention blocks for every gated-latent one. Liquid runs short convolutions in twenty-two of thirty layers. Neither got there by making ordinary quadratic attention run faster.

What this leaves you with

The local cheat code is ②, and sparsity does nothing for it. A 2.8T Mixture-of-Experts model is a serving-economics story: it makes tokens cheap for whoever owns the cluster. A 2.6B dense model is a laptop story: it makes tokens free for whoever owns the laptop, at the cost of knowing much less.

Those are different products that happen to share a benchmark column. If someone tells you a model is fast, the useful follow-up is which of the three numbers they shrank, and what they gave up to do it.

Glossary

Reference, not prerequisite. The nouns in this field are mostly stable; the counts are where people get misled, so each entry says what is being counted.

parameter
One number the model learned during training. Counted: 2.8 trillion of them in Kimi K3, 2.6 billion in LFM2.5‑2.6B.
weight
Effectively a synonym for parameter. Strictly, the parameters that multiply an input, as distinct from biases. “The weights” as a plural noun usually means the shipped file you download.
bias
A learned number that is added rather than multiplied. Most current transformers omit them, which is why the weight/parameter distinction has stopped mattering.
token
A chunk of text, roughly three quarters of a word, mapped to an integer. Not part of the model. Watch out: the word is used for three unrelated counts — the ~200,000 distinct entries in the vocabulary, the couple of thousand in your prompt, and the tens of trillions read during training.
vocabulary
The full set of distinct tokens the tokenizer knows. Fixed per model. Its size is the number of columns in the final unembedding matrix.
context window
The maximum number of token positions the model can hold at once. 1M for Kimi K3, 32K for the LFM2 family. Different from training tokens, which is total text ever read.
embedding
Drifts. Means both the vector that represents a token and the lookup table that produces those vectors. Occasionally also the whole technique.
active vs. total parameters
In a Mixture-of-Experts model, only some parameters run for any given token. Active governs speed; total governs memory. Quoting one without saying which is the most common way these figures get misreported.
expert
One of many parallel sub-networks in an MoE layer, of which a router picks a few per token. Kimi K3 fires 16 of 896.
prefill / decode
Prefill reads the whole prompt in parallel and is compute-bound. Decode emits one token at a time and is memory-bound at batch 1. They have different bottlenecks, so “fast” usually needs to say which.
KV cache
The stored key and value vectors for tokens already processed, so they never get recomputed. The only thing here that grows while the model is running.
quantization
Storing each weight in fewer bits. FP16 is 2 bytes per weight, BF16 the same, MXFP4 and Q4 about half a byte. It shrinks both ① and ② at once, which is why it shows up in every deployment story.
GQA / MLA
Grouped-query and multi-head latent attention. Both shrink the KV cache by sharing or compressing what gets stored per token, without changing the number of layers that store something.
linear attention
A family of mechanisms that replaces the growing cache with a fixed-size running state, so cost per token stops depending on how far you are into the sequence. Kimi Delta Attention is one; gated convolutions achieve a similar effect differently.
n and d
n is sequence length, the number of rows in the context matrix. d is model width, the number of columns. dₖ is the per-head slice of d used inside one attention head. Nearly every cost in this piece is some product of those two.
