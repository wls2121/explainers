dbt Semantic Layer: logic vs. serving

Define metrics for free. Pay to serve them to tools. Here’s where the line falls.

Four pieces. One writes the SQL — that’s MetricFlow, open source, and it runs locally in dbt Core for nothing. The other three carry the request in, run it, and hand the answer back. That’s the part you pay for.

The path a query takes

When someone drags “revenue” and “region” into a dashboard, nobody writes SQL — it gets generated in the middle.

authenticate compile serve / execute transport

Three stops do the work. The gateway authenticates you before any SQL exists. MetricFlow compiles your request into warehouse SQL on the fly, reading the manifest you built in Git. Your warehouse runs it and returns the rows. The rest just carries bytes.

Clicks become SQL

The tool sends metrics and dimensions, not tables:

{
  query(metrics: ["revenue"], groupBy: ["customer__region"]) {
    region
    revenue
  }
}

MetricFlow reads the manifest, finds the join path from orders to customers, picks the aggregation, and emits SQL in your warehouse’s dialect — written fresh for this request. That’s why a table of pre-computed numbers can’t stand in: change the slice and the table is wrong.

select
  customers.region        as region,
  sum(orders.amount)      as revenue
from analytics.orders      as orders
left join analytics.customers as customers
  on orders.customer_id = customers.id
group by 1

Where thin wins

dbt authenticates the caller, compiles the request to SQL, and routes the result; your warehouse stores and computes everything. For a team already on dbt and a cloud warehouse, that keeps things simple. Metrics read the same tables as every other query, so there’s no second copy to sync and no staleness gap. Every query runs in your warehouse, so its row-level security, column masking, and audit logging apply on their own — to analysts and agents alike. The compute is your warehouse’s, which you already run and budget for, so there’s no parallel tier to operate. Because dbt writes SQL per request, an agent asking for a slice nobody pre-computed gets an answer instead of a cache miss, and because access is enforced at the warehouse, that agent sees exactly what its role permits rather than whatever a shared token could reach. The tradeoff is latency on repeat queries, which is what caching handles.

So: define for free in dbt Core, query from the CLI, and pay for the managed endpoint that lets any tool or agent ask for a metric and get the same governed answer — without seeing your schema or writing SQL.
