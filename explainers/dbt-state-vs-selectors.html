source_status:fresher+ vs dbt State, visually

Why a selector can't reproduce the savings in your Cost Insights dashboard — even though both look at the same DAG. Same four scenarios, two lanes each: what the selector does, and what dbt State does.

1 · The whole thing in one idea: they ask different questions

A selector fires before anything compiles. It can only ask a coarse question about the graph. dbt State asks a precise question about each model's actual output.

source_status:fresher+
"Did any upstream source get new data?"
Yes/no, per source. If yes → rebuild that source's entire downstream chain. It can't know whether the new data changes any model's result, because nothing has compiled yet.
dbt State
"Would rebuilding this model actually change its output?"
Per model. It compares compiled code + upstream data state against the last build and skips the model when the result would be byte-identical.
The number in Cost Insights is exactly the gap between those two questions — every model the selector would have rebuilt that dbt State proved didn't need it.
New data / real change → must rebuild Source unchanged fresher+ rebuilds it anyway (wasted) dbt State skips it (saved)

The new rows are EU; the filter drops them. dbt State compiles stg_orders, sees the result is byte-identical, and skips it — so nothing downstream runs. The selector has no way to see that: "fresher" is true, so the whole chain rebuilds.

3 · Run the same job twice with no new data

The clearest test. Run your job, then run it again five minutes later — nothing changed upstream in between.

# selector has no memory of the last run's DATA state
$ dbt build --select "state:modified+"    # run 1  → builds N models
$ dbt build --select "state:modified+"    # run 2  → builds the same N models AGAIN

# dbt State tracks shared model-level state across runs
# run 1  → builds N models
# run 2  → 0 models (no upstream source changed → nothing to do)

Straight from the dbt docs: run state:modified twice and it builds all modified models both times; dbt State only reruns on the second pass if upstream sources actually changed.

dbt State has semantic understanding of the SQL — it compares the logical plan, so whitespace, comments, and alias renames don't count as a change. state:modified only checks whether the file's text changed, so it rebuilds. In an active repo, cosmetic churn adds up.

6 · Why you can't rebuild this with a selector

This is the honest framing for the engineering team — no correctness risk either way, just a big efficiency gap.

What selectors detect
That something upstream touched the graph — a timestamp moved, a file's text changed. Coarse, and computed before compile.
What dbt State detects
Whether the model's output would actually differ — compiled code + real upstream data state, per model.
The catch
A selector runs before any compile or diff. It has nothing to compare against beyond "did a timestamp move," so it must over-rebuild to stay safe.
Bottom line: source_status:fresher+ and state:modified+ are blunt triggers. They catch every real change (safe), but over-rebuild by design. dbt State is the only thing that asks "would the output actually differ?" for each model — and the savings you're already seeing is that question, answered a few hundred times a day.
